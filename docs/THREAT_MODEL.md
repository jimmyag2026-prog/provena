## Out of scope (v0.x)

- Availability: a hub can refuse service; it cannot do so undetectably for already-receipted entries. Mitigation: `provena mirror` keeps the same log (same roots) on a second hub that anyone can clone from.
- Truthfulness of measurements (see GUIDE §7).
- Challenge scores: a third party can audit inputs, rules and timing but cannot re-run scoring without the evaluator granting the predictions; the scorer is organizer code run only with `--yes`, sandboxed where bwrap / sandbox-exec exist (no network, no reads of Provena keys, writes only to its work directory) and resource-limited everywhere; it is not a hardened VM. On macOS a program can still read same-user processes' environments (so `PROVENA_PASSPHRASE` must not be set when scoring; `--sandbox require` enforces this) a child that calls `setsid` leaves the process group; such descendants are found by a per-run environment tag and killed when the run ends, unless they remove the tag first (they stay sandboxed). On Linux the PID namespace prevents both.
- Metadata privacy: entry counts, timing, member cards and the DAG shape of private projects are visible to the hub. Signed tree heads (size, root, time) of private projects are deliberately readable by anyone who knows the project id, so independent witnesses can check them for forks; entries and ciphertext are not.
- Selective bundles do not prove the author was still authorized at signing time (full bundles do).
- TSA certificate chains are reported, not validated against a root store.
- Key compromise before the first anchor: an attacker with the key and the hub's cooperation can forge history that predates the earliest anchor.
