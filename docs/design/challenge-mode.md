# 设计稿：Challenge 模式（预注册、盲测、多团队基准）

**Status: draft for decision** · 2026-10-31 · C1（SET 进证明包）、C2（跨项目引用）已实现；C3 以**实验性** `provena challenge init|submit|close|score|audit` 实现（`score --include-late` 也为迟交评分但标明迟交）（按本稿推荐默认：预测只给评审方、评审方独立）；C4 与 §6 待拍板

## 1. 要解决的问题

挑战赛 / 验证计量制度的公信力来自四件事，传统做法全靠「相信组织方」：

| 需要证明 | 传统做法 | Provena 做法 |
|---|---|---|
| 真值在任何提交之前就已固定 | 组织方声明 | 真值以 `plan` 承诺登记，**RFC 3161 锚定早于开赛** |
| 每份提交在截止前完成且之后未改 | 邮件时间戳 | 团队在**自己的项目**登记预测，Hub 回执 + 锚定时间早于截止 |
| 评分程序是预先公布的那一份 | 组织方声明 | 评分代码哈希写进预注册方案；评分 activity 的 `harness_sha256` 必须一致 |
| 分数 = 评分程序(真值, 预测) | 无法复核 | 评分步骤可 `provena rerun` 复现，结果以 `replicate` 证明入账 |

盲性：组织方在截止前看不到任何预测（团队密钥不共享），团队之间互相看不到；截止后预测只 `grant` 给评审方，**不必公开**（保护团队 IP），公开的只有分数与证明。

## 2. 角色

- **组织方**（`org` agent + 人员）：公开项目，登记方案、真值承诺、评分代码。
- **参赛团队**：各自的私有项目与密钥；可有 `software` agent（AI 模型）作为作者。
- **评审方**（可与组织方分离）：持有评分 harness，接收 grant，运行评分。
- **见证人 / TSA**：独立时间与防分叉证据（已有）。

## 3. 流程（初版设计；已由 §3b 的实现取代，保留作背景）

1. **T−1 预注册**：组织方 `plan protocol.md`（规则、指标、评分代码哈希）；`plan truth.csv`（只上承诺）；`meta` 写明截止时间 `deadline`；Hub 锚定 → 「真值早于开赛」可证。
2. **T0 开赛**：`publish targets.csv`（题目公开）。
3. **提交**：团队 `provena run --used targets.csv … --out predictions.csv`（AI 团队用 SDK `run(model=…, harness=…)` + trace），`push`；把**选择性证明包**（只含承诺）发给组织方作为回执。组织方可 `attest --type capture`/`endorse` 记录「已收到」。
4. **截止 T1**：Hub 锚定；任何晚于 T1 的提交在验证时被标为 late（§4b）。
5. **揭示**：组织方 `reveal truth.csv --with-key`；团队 `share predictions.csv --to evaluator.card.json`（只给评审方）。
6. **评分**：评审方 `provena run --used truth --used <imported predictions> --out scores.json -- python score.py`；任何人可 `rerun` 复核（评审方 grant 后）。
7. **榜单**：评审方发布 `prove scores.json --full` + RO-Crate；每行分数附该团队提交的证明链接（`cite`）。

## 3b. 实现后的信任链（v2，2026-10-31 第六轮审查后重做）

第一版把「哪个是真值、截止时间是什么」放在证明包里的**未签名提示**中，组织方可以事后改指向、改截止时间；参赛队可以提交多次、截止后只挑最好的那份给评审。v2 的原则：**预注册方案的公开内容是唯一权威**。

1. 组织方先登记真值承诺、题目、评分程序，再登记方案；方案末尾有机器可读的条款块 `<!-- provena-challenge … -->`：真值条目、题目条目、评分程序 sha256、截止时间、可选的报名队伍名单。方案、题目、评分程序随密钥公开。
2. 参赛队的提交步骤**引用方案条目**（`activity.external`）；提交时发**全量证明包**，评审能看到该队项目的全部条目（内容仍加密）。
3. 评审只从参赛队收到的 `challenge.pvb` 取方案条目 id；要求方案与真值承诺都有受信的「早于截止时间」证据；每个队伍项目必须**恰好一个**引用该方案的提交步骤、**恰好一次**授权给评审，二者都早于截止时间；报名名单存在时作者必须在名单内且每个作者只计一次。
4. 分数以队伍 agent 与项目为键（不含本地路径）；评分程序只在 `--yes` 后以最小环境运行；有 bwrap（Linux）或 sandbox-exec（macOS）时默认在沙箱里跑（断网、读不到 Provena 密钥与评审方仓库、只能写工作目录），任何平台都有 CPU 时间与文件大小上限（`--sandbox auto|require|off`）。

第七轮审查后补强（v2.1）：

5. **真值不得提前泄露**：`close` 只能在截止之后执行，并发出组织方项目的**全量**证明包；截止之前组织方日志只能公开方案、题目与评分程序；其余每一条 `reveal` / `grant`（包括不带密钥的承诺开口——小标签文件可被哈希穷举，以及把真值换个条目再登记一份）都必须带受信 Hub 回执、且排序时间晚于截止时间，否则判定挑战作废。组织方项目应专用于本次挑战。曾是组织方项目成员（能读到真值）的 agent 不得参赛。
6. **报名名单登记「agent + 项目」**（`--team AGENT_ID:PROJECT_ID`）：只登记 agent 时，一个队可以在多个项目各提交一次、事后挑最好的（每个项目各自「恰好一次」都成立）。
7. **条款块无歧义**：恰好一个条款块、每个键恰好一次、`deadline` 与 `deadline-ms` 必须一致；条款块写明评分程序条目（不再按位置猜）；方案、题目、评分程序、真值都必须**公开**（随密钥揭示），仅授权给评审方的不算。`submit` 打印它采用的截止时间、评分程序哈希与名单。
8. **组织方给不同队不同条款**会暴露：某队的提交引用了组织方项目里的另一个方案时，评审报告「组织方分发了不同条款」，而不是把错算在该队头上。
9. 一个榜单证明包最多附 18 份提交（外部包上限 20），超出时提前报错。
10. **第三方审计**：评审方公开榜单内容；`provena challenge audit leaderboard.pvb --challenge challenge.pvb --hub URL [--submission 队伍包]` 不需要密钥，与评审方共用同一套检查（`_check_inputs`），重新推出每一行的队伍、项目、预测条目与是否按时，并要求评分步骤恰好引用方案、真值、评分程序与所附提交；不一致即失败。

11. **第九轮审查后**：按时/迟交只看预测与授权条目的**受信 Hub 回执**（剥掉回执只会变成「时间无法证明」并被拒，而不是「迟交」）；`audit --submission 队伍包` 发现被漏掉的按时提交即失败；评审方不得参赛；方案、真值、题目、评分程序必须是四个不同条目。

剩余的结构性限制：
- 评审方在截止前就能看到预测（授权必须在截止前，防止参赛队看了真值再决定是否交）；开放报名时它可以用马甲提交抄来的结果——请用报名名单。

- 开放报名（无名单）时，同一个人可以用多把密钥开多个项目（Sybil）——需要报名名单或机构身份凭证来约束；`score` 会提示这一点。
- 榜单附带各队的全量证明包：条目内容仍加密，但日志**结构**（类型、作者、时间、授权对象）公开——参赛请用专用项目。
- 分数是评审方的声明：第三方能核对输入、时间与评分程序哈希，但预测只授权给评审方，无法自行重跑；评分程序哈希固定的是代码，不是其行为（可能读网络或时间）。
- 账本之外的泄露（组织方私下发送真值文件）无法由账本发现。

12. **Hub 榜单页核对（2026-10-31，PR #34）**：规则下沉到 `provena.core.challenge`，CLI 与 Hub 共用。Hub 对已公开的榜单用**自己截至评分步骤**的日志与回执时间重做：每行的队伍/预测条目/是否按时、组织方是否提前披露、方案与真值是否在截止前上链、引用集合是否恰好一致、是否有重复行、已报名且按时提交却不在榜上的队。结论分五档：`ok`（全部核对且无遗漏）、`ok-open`（开放报名，无法判断遗漏）、`partial`（有行的项目不在本 Hub）、`fail`、`unchecked`（找不到方案、超过 100 行或 100 个报名队）。这只是**第二意见**：读者若不信任该 Hub，仍应自己跑 `challenge audit`；Hub 的判断用的是它自己的回执时间，与审计方信任的日志一致时两者结论一致。

## 4. 缺的三个原语（初版设计；实现见 §3b：用 `activity.external` + 附带证明包代替 `xref`，截止时间写在方案条款块里）

| # | 原语 | 为什么需要 | 设计 |
|---|---|---|---|
| a | **跨项目引用 `xref`** | 评分 activity 在评审方项目里，要引用各团队项目里的预测实体 | entity body 新字段 `xref: {project, entry, head}`；验证器要求附带对方项目对该 entry 的包含证明 + 受信日志头；导入的实体承诺必须与源实体相同 |
| b | **逐条目时间回执进证明包** | 「截止前提交」需要比「不晚于包头时间」更紧的上界 | bundle item 可带 Hub 的 SET（`integrated_time` 已签名）；验证器对受信日志的 SET 给出逐条目时间事实 |
| c | **截止规则** | 机器可判定 late | `meta.deadline`（ms）；验证器对每份 `xref` 提交输出 on-time / late（基于 b 或锚定时间） |

可运行演示：`examples/challenge_demo.sh`（组织方、两支队伍、评审方；最终榜单证明包引用真值与两份提交，均由受信 Hub 证据支撑）。

2. 评审方是否独立于组织方（建议独立：组织方定规则，评审方算分，二者都上账）。
