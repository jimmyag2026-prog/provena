## [0.2.0] - 2026-10-31

### Added

- `examples/pilot_internal.sh`: the internal race of PILOT.md §7.1 on a running hub with real public data (iris, pinned SHA-256), three registered teams, an outside audit; run on the trial hub 2026-10-31 (`docs/pilots/2026-10-31-internal-race.md`).
- The hub's front end is now the single-page app: `/`, `/p/{pid}` and `/p/{pid}/e/{hash}` (the URLs `provena cite` prints) serve it, and it checks in the browser — a project's whole log (`verifyPublicLog`) or one entry's inclusion proof (`verifyEntryInclusion`) — and shows README (as text), files, lineage, leaderboard and the bundle drop zone. The server-rendered pages remain under `/classic/…` for clients without JavaScript (linked from `<noscript>`); `/app` redirects to `/`. New JSON: `GET /v1/projects/{pid}/entries/{hash}`; the overview carries the README text.
- `/app` (beta, now `/`): the first single-page reader; superseded by the SPA front end above.
- Hub orgs and quotas (ADR 0012): `hub serve --policy FILE` admits org agents (and, optionally, others under `default` limits), charges each project to its creator's org, enforces `max_projects` and `max_bytes` (stored ciphertext; freed when a redaction shreds it), and serves `GET /v1/orgs/{org}/usage` to holders of the org's API key (`provena hub api-key ORG`; only hashes are stored). The hub database now has a schema version with forward migrations and refuses a newer one.
- JSON twins of the hub pages: `GET /v1/catalog` and `GET /v1/projects/{pid}/overview` (entries, published files, lineage, leaderboard with the hub's check), built by the same functions that render the HTML, so agents read exactly what people see — the first step of the front-end split.
- Challenge rules live in `provena.core.challenge` (terms, on-time, one submission per team, early disclosure, eligibility), shared by the CLI and the hub. The hub's leaderboard card now re-applies them to its own logs and receipt times: a per-row check column, a verdict line, and registered teams missing from the board (flagged when they submitted on time). Still a second opinion; `challenge audit` checks without trusting the hub.
- Hub log key rotation (ADR 0010): `provena hub rotate-key --data DIR --yes` hands the log key over to a new one with a statement signed by both keys; `GET /v1/hub` serves the chain, the hub re-signs each project's latest head, and clients, witnesses and mirrors follow it (`W_HUB_KEY_ROTATED`; a key change without a hand-over is still `E_HUB_KEY`). Bundles carry `log_rotations`, and both verifiers trust the successor of a trusted log key — forward only.
- Replay snapshots (a cache, never evidence): the hub stores each project's replayed state every 500 entries and resumes cold loads from it (falling back to a full replay, with a log line, if the snapshot does not match the stored hashes); a checkout keeps `.provena/state.snapshot.json`, used only while the log prefix it covers is byte-identical. Resuming 10,000 entries takes ~4 ms instead of ~1.4 s; a hub cold load of such a project drops from ~1.6 s to ~0.3 s, because the hub still hashes every stored entry against its recorded hash and the signed head (damaged rows are quarantined as before). A checkout's snapshot carries an HMAC under a key in the user's Provena home (`snapshot.key`), so a snapshot written into a shared or synced checkout by someone else is ignored. `verify` and `doctor` still replay everything.
- C2SP checkpoints: `GET /v1/projects/{pid}/checkpoint` serves the latest tree head as a signed note and `/v1/hub/vkey?project=` its verifier key, so existing transparency-log witnesses can cosign Provena logs (ADR 0011).
- (integrator acceptance) `sdk.init(...)` creates the key and project without the CLI; `Project.plan_text(...)`; SDK `add`/`plan` and MCP `preregister` return the earlier entry for unchanged content (retries are safe; a step's outputs are always new); SDK paths fall back to the project root; preregistration rows carry `target` (upstream steps reached through lineage are marked) and `reason: order-unproven` when the order rests on the author's own head; MCP tools validate arguments against their schemas and return contract error codes with hints.
- Concurrent versions of one path (yours unpushed, a teammate's just pulled) are a conflict: `pull`/`push` exit 5 `E_CONFLICT`, `status` lists them, and `provena resolve PATH --keep HASH` picks the version this checkout tracks and checks out (fetching it from the hub if needed); both stay on the ledger.
- Proof Reader on every hub page: a dropped `.pvb` gets a plain-language meaning of its trust level and a preregistration table (proven / holds by the author's order only / not shown), in English or Chinese with the page; the reader is tested under Node with a stub DOM.
- Time-locked evidence: `provena seal DIR --reveal-after DATE` records every file of a data package and preregisters a manifest of their hashes (one proof shows the whole package existed by its anchor time); `provena unseal DIR.seal.json` publishes it all once the date has passed (`E_TOO_EARLY` before, `--force` to publish early — the ledger shows when).
- Built-in trust: the trial hub's log key and its TSA fingerprint ship with the release (`provena trust defaults [on|off]`, marked in `trust list`, named in verification output when they made the difference; `PROVENA_NO_DEFAULT_TRUST=1`), so a first `provena verify` of a bundle from that hub reaches `log-sequenced` / `anchored`. `docs/integrations/trial-hub.md`.
- Hub metrics for anchoring health (`provena_anchor_attempts_total`, `_failures_total`, `_last_anchor_attempt_seconds`, `_last_anchor_success_seconds`, `provena_anchor_independent`); `provena doctor` in verifier mode (no key or repository needed; automatic when neither exists); DEPLOY: monitoring that does not alarm on idle hubs, backup/restore and rollback runbook.
- `provena challenge status CHALLENGE.pvb --hub URL` (anyone, public data only: deadline, `open` / `awaiting close` / `closed` / `void`, when the truth was revealed, early disclosures, each registered team's activity; exit 7 when void) and `provena challenge join CHALLENGE.pvb --hub URL` (for open-registration challenges or after publication: a dedicated entry project on the challenge hub, and the `AGENT:PROJECT` line). Leaderboard rows name their protocol; the hub page ranks on-time rows above late ones. `examples/pilot_rehearsal.sh` runs the PILOT rehearsal against a live hub as agents would (passed on the DO trial hub, 2026-10-31).
- `hub serve --base-path /PREFIX` for a hub behind a reverse proxy that strips a path prefix (page links carry it); `deploy/do/` — the trial hub on the DO droplet (systemd unit with resource limits and filesystem protection, an append-only deploy log and `--expect <sha>` deploys, an idempotent Caddy route, setup notes).
- `provena mcp --project DIR`: an MCP server (stdio, no extra dependency) for AI agents — `record_step` (one call per tool/model call, files optional, failures included), `preregister`, `add_file`, `reveal`, `prove`, `verify`, `push`/`pull`, `log`, `status`; the key is unlocked once from a passphrase file and never enters the model's context; setup for Claude Code and Spark Research in `docs/integrations/mcp.md`. SDK: `Project.record(...)` and `sdk.verify(...)` (the `verify --json` verdict).
- `provena export intoto --step REF -o FILE`: a step as an in-toto Statement in a standard DSSE envelope (ADR 0011, predicate `docs/spec/predicate-run-v1.md`); `verify --badge SVG`; a GitHub Actions template in `examples/github-action/`.
- Ledger rules 2 (ADR 0009; new projects get them, existing projects keep rules 1, which are frozen): `member add --history` / `member history ID` hand a member the keys of earlier epochs (a recovery key or a member added after a rotation now reads history; the GUIDE recovery flow uses it); every step has a public `status` and a commitment to its sealed details, and `provena reveal <step>` publishes them for anyone to check (exit codes, models and parameters become provable); a file revealed without its content key can be revealed once more to publish it. The shared rule tables live in `docs/spec/rules.json`; both verifiers are tested against it, and randomized histories under rules 1 and 2 must agree in both.
- Fewer ids to carry: entries can be named `#N` (log position), by a hex prefix of at least 6 characters (errors list the candidates), or by path even in a clone that never checked the file out (sealed names resolve with your key); `provena config agent NAME` switches the key a checkout signs with; `trust add log --from-url URL` prints the key a hub signs with (`--yes` adds it); `trust add` confirms instead of printing the whole list; `clone` says it needs the full project id.
- `verify --json` / `provena --json verify`: `entries[]` (hash, index, kind, author, target, sequenced, time_bound, opened), `preregistration[]` (plan, activity, holds, ordered, reason — computed identically by the browser verifier), `evidence` (head signer, log trusted, witnesses carried, anchor providers), `checks.require.reached`.
- `provena --json-lines add a b c` prints one JSON line per file as it is recorded, then the envelope.
- Agent contract (`docs/spec/cli-contract-v1.md`): global `provena --json` prints one envelope (`provena-cli/1`: `ok`, `exit`, `data` with complete ids, `warnings`, `error{code,message,hint}`) on stdout and every human line on stderr — including usage errors and `run`'s own program output; exit codes 0–7 and 130 with contract error codes (`E_NO_PASSPHRASE`, `E_STRANDED`, `E_ROLLBACK`, `E_LATE`, …); `add`/`plan` skip content the same agent already recorded (`--force` to record again), `reveal`/`open` are safe to repeat, `checkout` exits 5 when files are missing or differ, challenge `void`/omitted exit 7.
- Hub project-creation policy: `provena hub serve --creators FILE` (allowlist of agent ids, re-read on every creation, fails closed) and `--projects-per-creator N`; refusals are 403. `hub serve` on a non-loopback address without `--creators` prints a note.

- `provena succeed NEW_AGENT|CARD`: planned key change from the CLI (previously Python only); the successor takes the role and every epoch key, the old key becomes inactive, and a local successor becomes the project's signing agent.

- `provena pull --from MIRROR_URL`: an existing checkout catches up from a mirror while the primary hub is unreachable. The mirror's key is pinned, its head must verify, and the root over our synced prefix plus its entries must equal that head; the entries are kept after the synced prefix (no mirror receipts mixed into primary bundles) until the next pull from the primary adds its receipts.

- `provena rerun --sandbox auto|require` runs a collaborator's recorded command in the same sandbox as challenge scorers (no network, no keys, home directory or repository; writes only to the workspace). Off by default: real analyses often need tools or caches under the home directory.

- A witness watching the same project on several hubs (primary and mirrors) remembers roots per size across hubs and refuses to cosign when two hubs disagree at a size or one does not extend the history another showed (consistency proof against the other hub's root).

- `provena mirror URL [--check]`: replicate the hub-sequenced log and its ciphertext to a second hub for availability; the mirror's receipts are checked and its head must have the same root as our log at its size (a difference is fork evidence). Anyone can clone from the mirror. The mirror's log key is pinned per URL.

- Provenance graphs draw inputs from other projects (`activity.external`) as their own nodes, linked to that entry's hub page (the scoring step of a challenge now shows protocol, truth, scorer and every submission).

- Hub project pages show a published `leaderboard.json` (from `provena challenge score`) as a ranked table, verified against the ledger first, with links to each team's project and a note on what `challenge audit` re-derives versus what is the evaluator's claim (Chinese and English).

- `provena verify x.pvb --json`: the verdict as one JSON object (`provena-verify/1`: valid, trust, project, head, targets, facts, notes, errors, trusted time bounds, `--require` / `--before` results, exit code) with the same exit codes, for CI and journal/registry integrations.

- `examples/challenge_cli_demo.sh`: the `provena challenge` commands end to end against a real hub with a real clock (registered `AGENT:PROJECT` teams, submit, close after the deadline, score, keyless audit); run by the CI `package` job on the built wheel.

- `provena challenge audit leaderboard.pvb --challenge challenge.pvb --hub URL`: anyone, without a key, re-applies the evaluator's own checks (one shared code path) to a published leaderboard — inputs, rules, each row's team, project, predictions entry and on-time status — and requires the scoring step to cite exactly the protocol, truth, scorer and attached submissions; only scores remain the evaluator's claim. `challenge score` now publishes the leaderboard content.
- Architecture design v0.1 (`docs/ARCHITECTURE.md`) and ADRs 0001–0004.
- Project skeleton: package layout, single-source version, CI, layering test.
- `provena.core` crypto primitives (M1): RFC 8785 canonical JSON (float-free subset), domain-separated SHA-256, Ed25519/X25519 agent identities with self-signed agent cards and scrypt keyfiles, chunked AES-256-GCM STREAM encryption, X25519 sealing, salted commitments; golden test vectors in `tests/vectors/core.json`.
- RFC 9162 Merkle tree with inclusion/consistency proofs, checked against the CT reference roots (M2).
- Signed ledger entry envelope: build, shape validation, signature verification, entry hash (M2).
- Ledger state machine `core.state.ProjectState` (M3): replay-derived membership, roles, key epochs, author chains, reveals, attestations, redactions; per-kind authorization rules.
- Pure entry builders `core.builders` (M3): project genesis, encrypted content with salted commitments, plans, activities, reveal/attest/redact, member add/remove/role, key rotation and succession.
- Local repository `.provena/` (M4): append-only log, content-addressed ciphertext blobs, tracked paths; per-user agent keyfiles under `$PROVENA_HOME`; local verification (replay, cid, plaintext-vs-commitment).
- `provena` CLI (M4): keygen, card, init, add, plan, run, log, show, cat, status, verify, member, rotate, reveal, attest, redact.
- Signed tree heads and proof bundles `provena-bundle/1` in selective and full modes (M5); offline verifier reporting established facts and time-trust level; CLI `checkpoint`, `prove`, `verify FILE.pvb` (spec: `docs/spec/bundle-v1.md`).
- Provena Hub (M6): FastAPI service with SQLite log storage and filesystem blobs; sequencing with Signed Entry Timestamps and per-append signed tree heads; public inclusion/consistency proofs; signed-request reads for private projects; blob acceptance bound to ledger cid/size; redaction deletes hub ciphertext (ADR 0005).
- Hub client and sync (M6): `provena remote` (pins hub log key), `push`, `pull`, `clone`, `hub serve`; every receipt, head signature, local root and head-to-head consistency proof is verified.
- `ProjectState.apply` is transactional: rejected entries leave no partial state.
- Sharing and publishing (M7): on-ledger `grant` entries seal one entry's content key and commitment opening to a non-member (an auditable access log); hub serves granted blobs to grantees' signed requests; CLI `share`, `open` (verify bundle → fetch → decrypt → check commitment), `publish` (reveal with key + push), `checkout` (members decrypt into the working tree).
- Witnesses and anchoring (M8): witness cosignatures over hub heads (cosign only after verifying consistency with the last head seen; `provena witness`); hub root-of-roots anchoring over all project heads with `self` and RFC 3161 providers (`hub serve --tsa URL`, `hub anchor`); bundles carry cosignatures and anchor records with consistency proofs; verifier trust levels `self-sequenced` < `log-sequenced` < `witnessed` < `anchored`.
- Minimal DER reader/writer and offline RFC 3161 token verification in core, cross-checked against a real freetsa.org token (ADR 0006).
- Web (M9): hub landing page with a drag-and-drop in-browser bundle verifier (`static/verifier.js`, WebCrypto only, no build step) and a public project explorer; private projects show only their head. The JS verifier is tested under Node for agreement with the Python verifier on valid and tampered bundles and on the shared golden vectors (RFC 3161 support added in M13).
- Python SDK `provena.sdk` (M10): `sdk.open()` → `Project.add/plan/run()/attest/reveal/read/log/prove/push/pull`; `run()` is a context manager that records outputs and records failed runs (with the exception type) before re-raising — for instruments, notebooks and AI agents. Hub sync moved to `provena.sdk.sync`; the CLI registers files through the SDK.
- W3C PROV-JSON export (`provena export prov`, `Project.export_prov`): public structure by default, decrypted names/commands/times only with `--include-private`.
- Hub hardening (M11): `MerkleLog` with cached perfect subtrees (100k appends with a root each in ~0.6 s; proofs O(log² n)); paginated entry listing followed transparently by the client; SQLite WAL + synchronous=FULL; `PROVENA_HUB_PASSPHRASE_FILE`; Dockerfile; `docs/DEPLOY.md`.
- Docs (M12): `docs/GUIDE.md` (user guide), `docs/THREAT_MODEL.md` (threat → defence → code → test), `docs/API.md` (hub HTTP API), `examples/demo.sh` (hub + researcher + reviewer + witness + anchoring, end to end).
- Browser RFC 3161 verification (M13): `static/rfc3161.js` — minimal DER/X.509 reader, CMS signed-attribute checks, WebCrypto RSA-PKCS#1 v1.5 / ECDSA (DER→P1363) / Ed25519; the web verifier now reaches `anchored`. Cross-tested under Node on the real freetsa.org token and local-TSA tokens.
- State replay ~9x faster (6,000 entries: 7.0 s → ~0.9 s): rollback snapshots only membership/epoch/wraps (additive collections are written last), and an entry is canonicalized three times instead of five.
- `provena lineage REF`: provenance tree of an entry (generating activity, plan, inputs, recursively) with reveal/redaction/attestation markers.
- Phase 3 design draft `docs/design/attested-capture.md`: capture-assurance ladder C0–C4 (capture daemon, hardware-held instrument keys, measured capture, facility co-signature) and AI-agent provenance (model id, harness hash, sealed trace commitments).
- Capture daemon (Phase 3 P3-1, level C1): `provena capture DIR [--once] [--push-every N]` / `provena.sdk.capture.Capture` registers instrument output under the instrument's own key once a file is stable across two polls; changed files become new versions referencing the previous entry; public `capture` metadata (`by`, `file_mtime`, `observed`); restart-safe state in `.provena/capture.json`. `Project.add` accepts `refs` and `capture`.
- AI-agent provenance (Phase 3 P3-4, first cut): `Project.run(..., model=, harness=)` records the model id and the agent program's sha256 in sealed activity details; `run.trace()` stores the agent transcript as an encrypted output (`application/x-provena-trace`) that can later be revealed for audit.
- Public project pages show a server-rendered provenance graph (layered SVG: inputs/plans → activity → outputs; revealed/redacted markers; no client-side code).
- Attestation types `capture` (a facility vouches it performed the measurement) and `operator` (who ran the instrument) for Phase 3 C4 facility co-signature; both verifiers report them like other attestations.
- Streaming blobs end to end: the hub spools uploads to disk and publishes only bytes whose size and sha256 match the ledger (no whole-blob buffering; re-uploads of stored blobs are ignored), serves downloads with `FileResponse`; the client streams uploads from disk and downloads to a temp file verified against the cid; `checkout`/`open` stream-decrypt and publish files only after the plaintext hash and commitment check. Verified with a 64 MB file over real HTTP (hub RSS ≈ 53 MB).
- Citations: `provena cite REF [--format text|bibtex|json]` and a hub landing page per entry (`/p/<project>/e/<entry>`) confirming existence, position, kind, hub sequencing time and first anchor; private projects show nothing more (the entry hash itself is the capability to look it up).
- `provena rerun ACTIVITY --yes [--attest]`: re-executes a recorded `provena run` step in a fresh workspace built from the decrypted inputs, compares every output with its ledger hash (match / DIFFERS / missing) and the exit code, and can record a `replicate` attestation with the verdict. Refuses to execute without `--yes` and always prints the recorded command and its author first.
- Hub abuse limits: per-client token buckets on writes (`--writes-per-minute`, default 120/min, burst 60) and project creation (20/h), a hub-wide `--max-projects` cap, `--behind-proxy` to honour X-Forwarded-For; 429 with Retry-After. Reads are not limited.
- Project card: new `meta` entry kind (title, description, license, tags; owners/maintainers; bounded plain strings), optional in genesis; `provena meta`; hub search (`/?q=`), titles/tags/licence on listings and project pages, `meta` in `GET /v1/projects/{pid}` for public projects; titles in BibTeX citations.
- GUIDE: key recovery with an offline second owner key.
- Browser verifier replays the full state machine for full bundles (`replayState`, rule-for-rule with `core/state.py`), so web verification of full bundles now proves authorization too. Cross-checked on a 16-case corpus of rule-violating logs (non-member, viewer write, chain gap, owner escalation, missing wraps, bad reveal, duplicate cid, provenance squatting, output-before-plan, demoting the last owner, booleans as integers…) plus a valid log using every kind.
- State machine: JSON booleans are no longer accepted where integers are required (Python `bool` is an `int`).
- Jupyter: `%load_ext provena.sdk.ipython` and `%%provena "description" --used … --out … [--plan …] [--model …]` record a cell as an activity with its exact source stored as an encrypted output; failing cells are recorded. Verified in a real IPython shell.
- RO-Crate 1.1 export (`provena export rocrate -o DIR [--metadata-only]`): decrypted files, schema.org File/CreateAction/agent nodes with `urn:provena:` identifiers and sha256, project card as Dataset metadata, and `provena-proof.pvb` proving every exported file against the ledger.
- Benchmarks (`scripts/bench.py`, `docs/devlog/benchmarks.md`); the bundle builder now uses one cached Merkle tree and the precomputed entry hashes (selective bundle on 10k entries 813 → 220 ms) and full-bundle verification no longer replays the log twice (3.0 → 1.6 s).
- Hub blob storage behind a `BlobStore` interface: `FsBlobStore` (default) and `S3BlobStore` for S3-compatible object stores (AWS S3, DigitalOcean Spaces, MinIO, R2); `hub serve --s3-bucket/--s3-prefix/--s3-endpoint`, credentials only from the standard AWS chain; optional extra `provena[s3]`. Uploads are still checked locally before an object is written; redaction deletes the object. Tested end to end against moto.
- `provena ui`: local, read-only browser view of a repository (ledger with decrypted names and commands, provenance graph with names, entry pages with public body and locally decrypted sealed fields, text previews and downloads, one-click verification, members). Bound to 127.0.0.1, one-time token + cookie, strict Host check, `script-src 'none'`; keys and plaintext never leave the process. Deliberately not a hub feature: the hub is untrusted and must never serve code that handles keys.
- `provena doctor`: end-to-end setup check (key exists/unlocks, ledger verifies, ciphertext present, membership, hub reachable with the pinned key, hub trusted, everything pushed, witness/anchor evidence) with the fix for each failing item; `provena status` reports hub sync state.
- Hub metadata on PostgreSQL: one portable SQL layer for SQLite (default) and PostgreSQL (psycopg 3, optional extra `provena[postgres]`), selected by `PROVENA_HUB_DATABASE_URL` (environment only: DSNs carry passwords). Tested end to end against a throwaway local cluster, including restart and witness cosignatures.
- Identity credentials: an `org` agent signs who holds an agent key (name, affiliation, ORCID iD, email, role; issued/expiry) — `provena identity issue|attach`, `provena trust add org`, bundles carry credentials for their authors; both verifiers report them as facts only for trusted orgs and only if valid at the bundle head's time. Identity never changes the time trust level. Claim text uses a Unicode-version-independent check so Python and JS cannot disagree.
- Design draft `docs/design/challenge-mode.md`: preregistered, blinded multi-team benchmarks on Provena (truth committed and anchored before the call, on-time sealed submissions in each team's own project, grants to an independent evaluator, reproducible scoring) and the three missing primitives (cross-project `xref`, per-entry SET time evidence in bundles, deadline rule).
- Signed entry timestamps (SETs) travel in proof bundles: both verifiers check each receipt against its entry, position and the head's log and, for a trusted log, state the entry's own sequencing time (tighter than "no later than the head"); a receipt dated after its head invalidates the bundle (challenge-mode primitive C1).
- Inputs from other projects (challenge-mode primitive C2): `activity.external` cites `{project, entry}` pairs in other projects (`provena run --external P:E`, SDK `run(external=…)`); proof bundles attach those projects' own bundles (`prove --external other.pvb`), which both verifiers check with the same trust sets (one level, max 20) and report as "used entry … of project … (that project's evidence: <trust>)".
- `examples/challenge_demo.sh`: a full preregistered, blinded challenge with today's primitives (organizer, two teams in private projects, evaluator; grants, reveal after the deadline, scoring that cites every input across projects; one verifiable leaderboard bundle).
- Reveals can publish the file name (`reveal --with-name`; `publish` does so unless `--keep-name-sealed`), so `provena open` writes published files under their real names.
- Hub `/healthz` (database reachable; lists quarantined projects) and `/metrics` (Prometheus: projects, quarantined, entries, free upload slots, anchors, last anchor time); monitoring section in DEPLOY.md.
- Hub pages in Chinese and English (Accept-Language, `?lang=zh|en`, switch in the header); ledger rows link to their citation pages.
- CLI split into modules (`cli/common.py`, `ledger.py`, `proofs.py`, `hubcmds.py`; parser in `main.py`), mechanically, with no behaviour change.
- ADR 0008 (proposed): cryptographic agility and post-quantum migration — evidence carried by hash chains plus periodic re-anchoring, algorithm-versioned tags/cards, hybrid Ed25519 + ML-DSA signatures and X25519 + ML-KEM epoch-key wraps; v1 records stay verifiable forever.
- Re-anchoring (ADR 0008 step 1): `hub serve --reanchor-days N` (default 30) re-stamps an unchanged root of roots so long-lived records keep collecting fresh time-stamps; the external TSA call now runs outside the sequencing lock (it used to block writes for the TSA round trip).
- `provena verify x.pvb --before 2026-11-01T00:00Z`: passes only if every target has *trusted* evidence (trusted-log head, signed receipt, or trusted-TSA anchor) of existing before the deadline; the report exposes these bounds as `time_bounds` for scripts (deadlines for grants, challenges, preregistration).
- Published files are downloadable from the hub (`/p/<project>/files/<entry>`, listed on project pages): for content revealed *with its key* the hub decrypts, checks the plaintext against the revealed hash and the ledger commitment, then streams it; content revealed without its key, redacted, or private stays ciphertext-only.
- A `README.md` published with its key is rendered as the public project card (verified against its revealed hash; a tiny Markdown subset applied after HTML-escaping, so ledger text never becomes markup).
- Concurrency stress test: 8 writers pushing to separate projects through one hub while 3 readers hit pages, `/healthz`, `/metrics` and anchoring; every stored log must replay to the head root in client order and reload cleanly.
- Release tooling: `scripts/bump_version.py X.Y.Z|major|minor|patch` bumps the single version source and dates the changelog section; it never commits, tags or pushes (tagging stays a maintainer decision). Tests enforce the single version source.
- Experimental `provena challenge init|submit|close|score` (challenge-mode C3) with the design's recommended defaults: the organizer commits the truth and publishes protocol, targets and scorer; teams submit in their own projects and share predictions with the evaluator only (submissions report ON TIME from trusted receipts); the organizer reveals after the deadline; the evaluator checks the scorer against the preregistered hash, runs it only with `--yes` and without `PROVENA_*` variables, scores on-time submissions and publishes a leaderboard bundle citing truth, scorer and every submission. SDK gains `Project.share` and `reveal(with_name=)`; SDK hub calls go through the same client factory as the CLI.
- Lazy project loading: the hub no longer replays every log at start-up; project state loads on first access into a bounded LRU (`cache_size`, default 2,000) under the write lock (a reload can never race a write); listings, counts and anchoring read a storage catalog; failed redaction deletes go to a persistent retry queue. Pre-catalog databases are migrated on first start. Cold start at 2,000 projects × 20 entries: 7.2 s → 0.1 s.

### Fixed

- A challenge project can no longer void itself by accident: `challenge init` refuses a project that already disclosed content, and `reveal`/`publish`/`share` of anything but the protocol, targets and scorer while its challenge is open need `--force`; `challenge status` names what was disclosed early (found by the internal race).
- Hub behind a prefix-stripping proxy (`--base-path`): signed requests were refused (401) because clients sign the path they send (`/provena/v1/…`) and the hub saw it without the prefix. Found deploying the DO trial hub.
- (agent re-tests of the CLI contract) Codes an agent can act on: a concurrent push or a hub moving on mid-sync is `E_CONFLICT` (exit 5, retry) instead of an input error; a local ledger edited outside Provena, a damaged JSON file (named) or damaged ciphertext is `E_CORRUPT` (exit 6) — `checkout` drops a damaged local blob so `pull` fetches a good copy; unknown references and agents are `E_NOT_FOUND`; a failed `run` is `E_PROGRAM` with `data.status`; an unregistered team is `E_FORBIDDEN` (4), closing early `E_TOO_EARLY` (5, with `deadline_ms`), a second different submission `E_CONFLICT` (5, with the existing hash), `score` without `--yes` `E_CONFIRM` (with the scorer path and sandbox), an audit without a trusted log `E_UNTRUSTED` with a hint naming the key; `verify`/`doctor` failures carry an error, `verify --content` for an entry the bundle does not open is a usage error and `checks.content` records the check. `run --json` keeps the program's stdout off the envelope; `run` reports `used`/`generated` as entries and warns about declared outputs that never appeared; `stranded list|redo` return the entries and the old→new hash map; `log --json` names other members' files; `status` lists changed paths; `rotate` auto-pushes and returns its entry; commands that auto-push say `pushed`; `challenge close` is idempotent; sandbox and registration notes go to `warnings[]`; envelopes name subcommands (`challenge score`); preregistration records carry `proven` (holds and ordered by a trusted log) in both verifiers; symlinks pointing outside the project are refused.
- (Phase 0 review) `run` without declared files no longer hangs when its own stdout closes (`provena run -- yes | head`), and a step with `--out` keeps its terminal (a step whose outputs never appear is recorded through a short note); hub passphrase files mounted by Docker/Kubernetes (0444, root-owned) are accepted again and whitespace-stripped as before; `add` refuses exactly the names collaborators' checkouts refuse (`.git/…`, `.PROVENA` on case-insensitive disks, `:`, `\\`); agent names from before keep loading; mirroring from a mirror clone and rehoming to a hub that is itself a mirror are refused, and only owners/maintainers record a primary (its URL may move); a hub rolled back and then written to is named as a rollback (exit 6); `challenge submit` resumes a submission cut short by a failed push; SDK `push`/`pull` raise `SyncIncomplete` when entries were set aside, and `sdk.open` reads `PROVENA_PASSPHRASE_FILE`; `stranded redo` warns when the file changed and keeps its media type; `encrypt_stream` refuses chunk sizes `decrypt_stream` would refuse.
- (agent testing, Phase 0) Syncs no longer look complete when they are not:
  - Rate limits (429 with `Retry-After`) are waited out and retried (bounded by `PROVENA_RETRY_WAIT`, default 120 s), so a large push resumes by itself.
  - A push that was cut short (killed, throttled, offline) is reported by `status` and fails `doctor` until a push finishes; a push ends by confirming that no file is missing on the hub.
  - Entries set aside because they no longer apply on the hub's log (e.g. after a concurrent key rotation) make `push`/`pull` exit 5, are shown by `status`/`doctor`, are untracked again, and `provena stranded list|redo` records their files anew.
  - The hub's log key is checked before anything is written (a reset hub at the same URL received the genesis); a rolled-back hub is named as such (exit 6) by `pull`, `push` and `doctor`, which also checks the live head size.
  - A checkout cloned from a mirror is read-only and points at the primary recorded by `provena mirror` (`POST /v1/projects/{pid}/primary`); `provena remote --rehome` moves it there (writing to the mirror forked the project).
  - `hub serve` refuses a data directory another hub process is serving; `doctor` counts only independent (RFC 3161) anchors.
- (agent testing, Phase 0) Inputs and non-interactive use:
  - No passphrase and no terminal is a one-line error (exit 4) instead of a traceback; `PROVENA_PASSPHRASE_FILE` / `PROVENA_PASSPHRASE_FILE_<AGENT>` (mode 600) for agents and services, also for `hub serve`; a wrong passphrase exits 4.
  - `add`/`plan` refuse files outside the project, inside `.provena/` and directories, checking a whole batch before recording any (an outside path stayed on the append-only ledger and stopped every collaborator's checkout); symlinks keep their own name.
  - Agent names are restricted to `[A-Za-z0-9._-]` (`keygen --name ../x` wrote outside the agents folder).
  - `run` without declared inputs keeps the program's output as a sealed transcript, so a failed step that wrote nothing is recorded instead of rejected after it ran; files on the command line count as inputs before that check.
  - SDK `run(params=)` normalizes floats, big ints, paths and tuples before the tool runs; a recording failure never replaces the tool's own exception; steps without files are recorded.
  - `reveal`/`prove --open` on an activity say why it cannot be opened instead of `KeyError: 'salt'`; corrupt JSON, directories, permission errors and Ctrl-C print one line instead of a traceback.
- (agent testing, critical) Two writers on one project — two `provena add` processes, two SDK `Project` objects, or an SDK object used after a CLI command — forked the author's chain and left the ledger permanently unreplayable. Local writes now take an exclusive lock on `.provena/lock`, reload the log if another writer appended, and build each entry on the latest state; an entry prepared on a stale state is refused ("run it again") instead of written. `pull`/`push`/`mirror` hold the same lock; small JSON files use unique temp names.
- Hub: the first `POST /v1/anchors/run` was refused as "too recent" on a machine booted less than 30 s earlier (the throttle started at monotonic time 0).
- (sync review, high) Own unpushed entries built on a mirror entry the primary never confirmed (e.g. an attestation on it) made every later pull and push fail; `pull` now replays pending entries one by one and sets the ones that no longer apply aside in `.provena/stranded.jsonl` with a warning. Also: `pull` fetches the hub's head first and reads entries up to it (a teammate pushing at the same moment no longer breaks it); a push overtaken by a concurrent one says so and asks to push again; receipts are saved before the sync point moves; mirror-read entries are marked provisional before they enter the log; files a teammate has not uploaded yet are reported, not fatal; mirror URLs with IPv6 hosts or bad ports are handled.
- (review of `pull --from`, high) Entries read from a mirror sat with the user's own unpushed entries, so `push` relayed mirror-only entries to the primary under the user's request and an equivocating member could wedge the user's pulls; mirror-read entries are now tracked as provisional, dropped by the next primary pull unless the primary confirms them, and never pushed. `pull --from` requires a mirror pinned with `provena mirror` or a trusted log key (no trust on first use), checks each mirror head against the one it showed before, fetches any missing ciphertext without failing the pull, and `doctor` / `prove` report provisional mirror entries separately.
- (final regression review) `pull` now fetches every readable entry's missing ciphertext, not only this pull's new entries: `push`, `mirror` and the automatic push after `member` / `reveal` / `redact` advance the sync point without downloading, and a teammate's new file then stayed unreadable. `run --out ./r.json` (any spelling of a named file) records the file even when the step reproduces it unchanged. Both verifiers reject a non-integer `witnesses` policy; mirror pins use one normalised URL spelling; `trust remove` also removes oddly stored values; `run --no-auto-inputs` turns off recording command-line files as inputs.

- `provena run` as the guide writes it (found by a docs walkthrough): `--used raw/` takes a directory (its files) instead of crashing; `--out results/` records only files the command created or changed, not every file already there; repository files named on the command line (e.g. `fit.py`) are recorded as inputs, and a changed input is registered as a new version; `rerun` recreates output folders. A step recorded exactly as in the guide now replicates.

- Demo scripts wait for the hub's `/healthz` instead of a fixed two-second sleep (a cold first run from a fresh install lost the race); a stray test-vector file is no longer shipped in the sdist. CI gains a `package` job that installs the built wheel and runs both demos.
- Witness cosignatures on an earlier hub head were dropped from bundles built on a later head (found by `examples/demo.sh`). Bundles now carry cosignatures on any earlier head with a consistency proof to the bundle head (`GET /v1/projects/{pid}/cosignatures/latest`), in both verifiers.
- RFC 3161 tokens must carry an ESS signing-certificate attribute (v1 or v2) whose hash matches the signer certificate (RFC 3161 §2.4.1 / RFC 5816), in both verifiers.
- (security review #1, critical) Trust levels were inferred from the bundle itself: a throwaway log key read as `log-sequenced`, a self-made witness as `witnessed`, a self-signed TSA certificate as `anchored` — enough to backdate genuine entries, also in the hub's web verifier. Trust now comes only from the verifier's trust sets (log ids, witness ids, TSA certificate fingerprints; `provena trust`, `--trust-*`, `--require`), untrusted evidence is reported as a note, a new `unverified` level exists, an anchor earlier than its head is invalid, and the web verifier trusts only its own hub's log key and TSAs (ADR 0007).
- (security review #4, high) A `key succeed` entry whose successor card lacked `id` passed validation and then crashed outside the rollback, leaving a half-applied succession; the hub then failed to restart. Card `id` is now mandatory, `_record` uses validated values only, the hub reloads a project from storage if persisting fails, and a project whose log fails replay is isolated (503) instead of preventing startup.
- (security review #3, high) Hub blobs were stored globally by cid while access was decided by a per-project map any entry could extend: another project could alias a private cid to read it anonymously or shred it with its own redaction. Blobs are now stored and authorized per project, and the state machine allows each cid to be registered by only one entry per project (stops in-project aliasing to publish/share/shred someone else's data).
- (security review #2, high) "preregistration holds" only compared plan vs. activity position, so results registered *before* the plan could be claimed as generated under it (HARKing). The state machine now requires every generated entity to be registered after the cited plan and to be generated by at most one activity; both verifiers state preregistration only when all outputs are proven to follow the plan.

### Changed

- The core installs and verifies without `httpx` (`pip install provena` records, proves and verifies offline; `[client]` adds the hub commands); CI checks the bare wheel.
- `push` asks the hub which blobs it lacks in one request per 1000 (`POST /v1/projects/{pid}/blobs/missing`) instead of a HEAD request per local blob.
- The project policy's `witnesses` count is now enforced by both verifiers: `witnessed` requires at least that many distinct trusted witnesses whose cosigned heads cover every target (default 1); with fewer, the bundle stays `log-sequenced` and a note says how many were found.

- From a second guide walkthrough: `prove` warns when entries are not yet pushed (the bundle can then be at most self-sequenced); a removed member's key gets a clear error instead of a traceback; the guides add the witness keygen, `pull` before `prove` to carry cosignatures, `push` before proving a new step, and re-mirroring after a redaction.

- When preregistration is not shown, both verifiers now say why: some outputs of the step are not in the bundle (prove them too, or use a full bundle), or an output was registered before the plan.

- From a step-by-step walkthrough of the user guide: `provena member list`; `member rm` / `role` accept a unique id prefix (as `provena log` shows ids); `reveal`, `redact` and `member` changes are pushed at once when a hub is configured (as `share` already was), and `redact` says when the working copy is still on disk; `trust add` rejects anything but a full agent id or a full 64-hex TSA fingerprint; `doctor` shows fixes only for failed checks and no longer fails on optional ones (witnesses, anchors, hub); `export rocrate` warns that the crate holds decrypted files; `challenge init` and `score` need a configured hub up front (a challenge set up without one could never be scored); `ui` prints its URL even when output is redirected.
- **Breaking (pre-release, no migration provided):** hub blobs moved to `blobs/<project>/<cid[:2]>/<cid>`; logs that violate the new rules (outputs before plan, duplicate generator, duplicate cid, foreign generated entity) no longer replay. Recreate dev hubs/repos made before 2026-10-31 02:00 CST.
- Trust upgrades (`witnessed`, `anchored`) now require the evidence to cover every target entry.

### Security

- (review of phases 2–6) A rules-2 step's public `status` must agree with its revealed exit code (both verifiers, full and selective bundles); MCP `prove`/`verify` read and write `.pvb` files inside the project only and never overwrite other files (a prompt-injected agent could clobber any file); `challenge status` replays the organizer's public log, checks receipts against the log key the challenge bundle names (not the one the hub reports) and counts any early disclosure as the evaluator does; `resolve` refuses to overwrite unrecorded local edits (`--force`) and takes the write lock; `trust remove` drops a single built-in id (ADR 0007 amended for built-in defaults); the browser verifier treats `policy.rules: null` as invalid like Python; in-toto export is limited to the exporter's own steps.
- (agent testing, Phase 0) Challenges: an early snapshot of a team's full log hid a second submission, so "exactly one submission" depended on which bundle the evaluator was given. `score`/`audit` now fetch the public tree head one entry past each team bundle and refuse the bundle if that entry was sequenced before the deadline; `submit` refuses a second submission and exits 7 when late; `audit --submission` checks that the board scored that bundle's entry; `challenge init` refuses a past deadline and a second challenge in the same project.
- `decrypt_stream` refuses a chunk size above 16 MiB (a key holder could make a decrypting hub allocate up to 4 GiB per chunk).
- (agent testing) `verify --content ID=FILE` reported a match without looking at FILE when the bundle embedded the plaintext, and silently ignored content for entries the bundle does not open. Both verifiers (Python and browser) now check embedded and supplied content separately and reject supplied content they cannot check.
- Sandbox (macOS, and Linux without bubblewrap): descendants that called `setsid` left the process group and outlived the run; every run now carries a random environment tag, and processes still carrying it are killed when the run ends (best effort: a program can remove the tag before detaching).
- Linux sandbox (first real run, in CI): the empty mounts hiding the home and temp directories were writable, so a scorer could write beside its work directory into memory; they are now remounted read-only after the work directory is mounted, and hidden paths nested in another hidden path are no longer mounted twice. A `sandbox-linux` CI job runs the sandbox tests under bubblewrap.
- `challenge score` runs the organizer's scoring program sandboxed when the platform allows (`--sandbox auto|require|off`; bubblewrap on Linux, `sandbox-exec` on macOS): no network, writes only to its work directory, the Provena home (keys) and the evaluator's repo state unreadable; always under CPU-time, file-size and no-core-dump limits. A failing or overlong scorer is a clear error, not a traceback.

- Cold loads of evicted projects are capped (4 at a time, `Hub(cold_loads=)`); a request that cannot get a slot within 30 s gets 503, so a flood of reads for cold projects cannot occupy every worker thread (eighth-review suggestion).
- Guarded against a FastAPI pitfall where postponed annotations turn a `Depends` auth check into an optional query parameter (private-read bypass); covered by tests.
- Ledger-supplied file names are sanitised before writing (no absolute paths, `..`, or anything under `.provena/` or `.git/`).
- (security review, low) pull checks each receipt's index and project; witnesses pin each hub's log key and check the head's project; the browser verifier enforces the exact tree-head field set and 31-bit integer indexes; absurd client timestamps no longer break pages or CLI output; per-project anchor records are cached per anchoring round.
- (second review) Only an entity's author or an admin may record the activity that generated it (stops provenance squatting); order-based statements (`#n`, preregistration) are facts only under a trusted log, otherwise notes; selective bundles reject an author `prev` pointing forward; the browser verifier accepts a genesis only at index 0; evidence heads may not be dated after the bundle head; `create_project` refuses quarantined projects and cleans up on persist failure; `push` checks receipts like `pull` (signed entry hash, position, project, genesis receipt); hex ids reject trailing newlines; malformed entry bodies are verification errors (422), not 500s; hub startup isolates any replay exception.
- RO-Crate export wrote ledger-supplied file names without sanitising (path traversal by a co-member); ledger path checks now live in `store.paths.safe_relpath`, shared by checkout, open, rerun and the RO-Crate export.
- Lone UTF-16 surrogates: Python raised a raw `UnicodeEncodeError` (hub 500) while the browser escaped and accepted them, splitting the verifiers. Both canonicalizers now reject them; a seeded 400-value fuzz test checks byte-identical canonical JSON and hashes across Python and JS. CI installs Node 22 for the parity tests.
- (third review, high) Stored XSS: the citation page rendered an arbitrary `commitment` field from non-content entries; it now shows only hex commitments of entity/plan entries, and every hub response carries a strict Content-Security-Policy (`script-src 'self'`), `nosniff` and `no-referrer`. BibTeX titles are sanitised against LaTeX injection.
- (third review, high) Upload disk-fill: uploads were spooled up to 1 GiB regardless of the ledger size and temp files survived client disconnects. Uploads now stream into the project's blob directory capped at the ledger size and hashed on the fly, temp files are removed on every exit path and swept at startup, concurrent uploads are bounded (16), and publication is re-validated under the sequencing lock (a redaction sequenced mid-upload wins). Clients bound downloads by the ledger size.
- (third review, medium) Rate-limit buckets never shrank (unbounded memory, event-loop stalls): now an LRU with a hard key cap. IPv6 clients are keyed by /64. `--behind-proxy` uses the rightmost `X-Forwarded-For` entry (the one our proxy added), not the client-controlled leftmost.
- (third review, medium) Browser/Python divergences: JS now ports `check_shape` completely (`ts`, `sealed`, `refs`, `body`, `project`/`prev` types), checks meta keys as own properties and counts lengths in code points. Both state machines enforce a strict per-kind whitelist of body fields (and a `capture` schema), so no entry kind can carry arbitrary extra data.
- (third review, medium) Ledger paths are checked case-insensitively and against Windows tricks (`.GIT`, `.git.`, `a:b`, backslashes, control characters). `rerun` shows the command shell-quoted, refuses control characters, lists the restored inputs as code, and runs the child without `PROVENA_*` variables (no passphrase leak). RO-Crate export verifies every file against its commitment, refuses entity names that collide with crate files, and includes recorded commands/times only with `--include-private`.
- Proving a result now includes the activity that generated it (and, recursively, its inputs and plan): the lineage walk followed only outgoing references, and activities point at their outputs (found by the challenge demo).
- Project creation burst raised from 3 to 10 per client address (`Limits.project_burst`): a lab behind one NAT address hit the limit on its fourth project (found by the challenge demo).
- (fourth review, medium) Identity credentials: checked at the head time, so they now become facts only under a trusted-log (or witnessed/anchored) head — a backdated throwaway-key head can no longer revive an expired credential; a credential that does not check out is a note, never fatal; bundles carry only credentials of their own authors (no leaking other members' names/ORCIDs); `identity attach` refuses expired credentials; claims reject bidi-control and zero-width characters; validity times must be integers (Python/JS parity).
- (fourth review, medium) Redacted ciphertext is never served even if a storage delete failed; deletes run outside the sequencing lock, failures are logged and retried at every start. S3 uploads publish outside the lock (re-checked for a redaction afterwards), and entry/project writes run in worker threads, so a large upload no longer stalls the hub. A project whose write and reload both fail is quarantined instead of serving phantom entries. S3 403 on HeadObject gets an actionable error; PostgreSQL connection errors never echo the DSN.
- (fourth review, low) Local UI: RFC 5987 download names (no 500 on non-Latin-1 names, no header-breaking characters), per-port cookie name, the URL token is moved into the cookie by a redirect, `no-referrer` and `nosniff`, the test Host only with an explicit test flag.
- Key succession required re-wrapping every key epoch, but a member who joined after epoch 0 never held the earlier keys, so their succession was impossible. The successor now re-wraps exactly the epochs the old key could read (Python and JS). Found by a new randomised test that replays 40 random valid histories (and swapped variants) through both verifiers.
- (fifth review, medium) `provena open` wrote files under names chosen by the bundle's author: it now opens only the bundle's targets, refuses hidden components (`.bashrc`, `.github/…`), paths escaping the output directory (symlinks included) and overwriting existing files without `--force`. `verify --before` fails on a bundle with no targets and on `--content` entries that are not targets.
- (fifth review, low) Parity and robustness: malformed relayed credentials are skipped (never invalidate a bundle) in both verifiers; `"receipt": null` is rejected in both; `activity.external` is shape-checked in both and JS uses own-property lookups; a cross-project citation is a fact only if the cited entry is a target of the attached bundle; proving one output no longer discloses its sibling outputs; `/healthz` reports a count of quarantined projects, not their ids; request threads iterate snapshots of shared hub state.
- Hub and local UI pages no longer overflow horizontally on narrow screens (long hashes in info grids and the header now wrap).
- (end-to-end red team, low) The web verifier now scans the raw bundle text and rejects float literals (`1.0`, `1e3`) like the Python verifier (JSON.parse had turned them into integers, so the browser said VALID where the CLI said INVALID). `HEAD` on a private project's blob requires the same signed membership as `GET`. Windows device names (`CON`, `NUL`, `LPT1.csv`…) are refused as ledger file names. Red team summary: no way found to make an honest verifier accept a false claim, read private plaintext or write files on another user's machine.
- (eleventh review, high) The scorer sandbox on macOS could be escaped through LaunchServices (`open` launched an app outside the sandbox with full access) and preferences/pasteboard services; it could inject keystrokes into the user's terminal; and it could read the rest of the home directory and the evaluator's working tree and publish anything through `scores.json`. Now: Mach service lookups and `lsopen` are denied; the home directory and the repository are unreadable except the Python runtime and the work directory; the program gets no terminal (stdin closed, its own session) and its process group is killed when it ends; on Linux bwrap runs with `--unshare-all --new-session`, a fresh `/proc` and the home directory hidden; scores must be finite numbers. `PROVENA_PASSPHRASE` in the environment is readable by any same-user program on macOS, so `--sandbox require` refuses to run with it set and `auto` warns.
- (twelfth review, medium) With the Python environment inside the evaluator's repository (a usual venv layout), the sandbox's final deny also blocked the interpreter, so every sandboxed scoring run failed and the only way out was `--sandbox off`; the interpreter and its packages stay readable while the rest of the repository stays hidden. The scorer can no longer signal (stop or kill) the user's other processes on macOS.
- The scorer sandbox also hides the system temp directories (other runs' work folders hold decrypted truths and predictions); only its own work folder is visible.
- (eleventh review, low) `provena run` refuses inputs and outputs that resolve outside the repository (a symlinked key file in `--used data/` was encrypted into the ledger); a failed automatic push says the change is saved locally and how to push it.
- (tenth review, high) The cross-hub witness cosigned a forked head smaller than every root it remembered, and the order of observation decided which hub was blamed: every head is now checked against the nearest smaller *and* larger root seen (the proof fetched from the hub that signed the larger head), a fork names both hubs, its evidence is kept, and the witness stops cosigning that project.
- (tenth review, medium) `provena mirror` first pulls from the primary, so a stale checkout no longer re-publishes ciphertext redacted elsewhere or calls an honest mirror "diverged"; mirror URLs are normalised for key pinning, `--check` pins too, and the mirror's signed head is kept as evidence. The hub's leaderboard card appears only for a board generated by a scoring step that cites other projects and published by that step's author, newest first, with finite scores (NaN / Infinity / huge numbers rejected; a huge integer used to fail the whole project page), and says plainly that the page has not checked it. - (ninth review, medium) A gated cold load could cache a snapshot that a write had overtaken (loaded inline, written and evicted meanwhile), reviving e.g. a removed member's read access until the next eviction; the loader now re-reads under the lock when the stored size differs. Storage errors while loading no longer quarantine a project until restart (only a failed replay does). Published downloads hold the cache file open, so a concurrent trim or shred cannot break the response.
- (eighth review, medium) Loading a project that is not in memory no longer stalls the hub: the replay runs outside the hub lock with one loader per project, and async routes load off the event loop (an anonymous GET of a large evicted project used to freeze every request, `/healthz` included).
- (eighth review, medium) A redaction landing during a cold decrypt of published content left the plaintext cached on disk: the cache file is now placed under the sequencing lock only if the content is still unredacted. The pending deletion is committed in the same transaction as the redaction (cleared only on success), so a crash or storage error is retried at start, plaintext cache included.
- (eighth review, low) Catalog rows commit in the same transaction as the genesis or meta entry (a failed catalog write could hide a committed project after eviction, and a retried create clobbered the cached log). Published content that fails verification is remembered instead of decrypted again per request; the plaintext cache is bounded (5 GiB, least recently used evicted) and crash leftovers are swept at start.
- (seventh review, high) Challenge truth disclosed before the deadline: `challenge close` no longer has `--force`, refuses before the deadline and needs a hub; it emits a full organizer bundle, and the evaluator requires every reveal or grant of the truth to carry a trusted-log receipt sequenced after the deadline (otherwise the challenge is void) and rejects teams that were ever members of the organizer's project. - (seventh review, medium/low) Challenge terms are unambiguous: exactly one terms block with each key once, `deadline` and `deadline-ms` must agree (plain digits), the scorer entry is named in the terms, and protocol, inputs, scorer and truth must be published rather than granted; `submit` prints the terms it applied. A team citing a different plan of the organizer is reported as organizer equivocation. More submissions than one leaderboard bundle can attach (18) fail up front. Docs: the leaderboard exposes each team's log structure (submit from a dedicated project).
- (sixth review, high) Challenge commands redesigned around the preregistered protocol as the signed authority: the protocol's published content names the truth entry, inputs, scorer hash, deadline and optional registered teams; teams cite the protocol; the evaluator takes ids only from the bundle teams received, requires trusted time evidence that protocol and truth commitment were fixed before the deadline, and requires each team's full log to show exactly one submission and one grant to it (no best-of-N), both before the deadline. - (sixth review, low) Python rejects float literals anywhere in a bundle file, matching the browser (and both ignore a UTF-8 BOM); published downloads are decrypted and verified once into a plaintext cache (cold decryptions capped at 4, 503 + Retry-After beyond), and redaction clears the cache; Windows device-name filter extended (`COM¹`, `CONIN$`, `nul .txt`).
